# HarmonyOS Design

把产品任务、平台能力和真实设备证据连成一条可执行链。始终区分长期成立的人因与状态原则、随 SDK 变化的平台能力，以及品牌或项目形成的 House Rule。

这是独立、非官方 Skill。不要把项目建议说成华为官方规定。

## Phase contract

1. **Input**：任务、目标窗口/输入、状态权威源和已有证据。
2. **Preflight**：确认信息架构、生命周期、设备和版本假设。
3. **Execute**：建立设计基线或完成 ArkUI 界面实现。
4. **Verify**：静态/编译后，固定目标并验证真实状态。
5. **Evidence**：记录状态模型、修改、截图和未验证项。
6. **Handoff**：业务实现交给 `harmonyos-develop`，体验验收交给 `harmonyos-review`。

## 最小任务契约

复用已知信息，只补会改变方案的缺口；无法确认时显式列为假设。

```yaml
主任务:
目标设备与窗口:
主要/次要输入:
目标_API_SDK:
主题_字号_语言:
产品状态权威源:
本轮范围:
完成信号:
验证方法:
假设:
```

不要在未确认窗口、输入和状态来源时静默套用手机触摸规则。

## 先建产品真相

在视觉和动画之前回答：

1. 哪个状态是权威事实，哪个只是本地缓存或视觉投影？
2. 状态是否混合了多个正交维度？
3. 哪个页面、组件或服务拥有数据和生命周期？
4. 冷启动、暖启动、返回、前后台、窗口变化和覆盖安装后会怎样？
5. 未知类型、过期响应、重复提交和失败恢复如何处理？

必要时先画状态表或转换图。不要用一个 `online/offline` 同时表达 App 链路、远端主机和会话存续；不要让“重新检查”暗示它能唤醒不可达进程。

## 决策顺序

1. 用户任务、信息架构与返回路径；
2. 状态权威、失败恢复与生命周期；
3. 设备、窗口、输入与内容密度；
4. 系统组件和平台默认行为；
5. 视觉 Token、字体、间距与层级；
6. 动效与手势；
7. 无障碍；
8. 性能与验证成本；
9. 品牌覆盖层。

## 实现规则

- 按下反馈只表示收到输入，不表示远端成功；分开 `acknowledged / pending / confirmed / failed`。
- 旧请求不得覆盖新意图；重复提交、失败、超时、取消和乱序要有策略。
- 页面只接收自己拥有或支持的数据；未注册类型默认拒绝或安全降级。
- Listener、timer、poll、request 和手势随 owner 生命周期释放。
- 优先使用系统控件、Navigation、滚动、焦点、无障碍和默认转场。
- 适配保持任务和信息架构，允许导航、密度、分栏和控件形态变化，不做简单等比缩放。
- 先确认 Window 是否已处理系统栏，再决定页面 inset，避免双重 safe area。
- WebView、IME、本地工具栏和远端内容几何要分清所有权。
- 动态列表使用稳定身份；语言、计数或状态变化要触发正确节点更新。
- 按下即反馈，手势跟手，离手从当前速度和位置继续，动画可被新输入打断。
- 动画完成不能作为业务完成时钟。
- 不发明 ArkUI API；以目标 SDK 声明、编译和设备行为为准。

## 实现与验证

当用户授权修改工程时：

1. 读取项目约束和相关代码，写出预期信号。
2. 复现问题或建立最小反例，定位系统性根因。
3. 设计最小兼容改动和失败关闭边界。
4. 一次完成一个连贯批次，先跑定向测试，再编译。
5. 构建通过后使用 `harmonyos-targets` 固定并租赁目标。
6. 验证关键入口、返回、按下/禁用、加载/失败、快速重复、反向打断和页面重入。
7. 按本次范围检查前后台、窗口变化、浅/深色、大字体、长文本和适用输入。
8. 对共享服务、路由、格式或生命周期补交叉回归。
9. 做完成挑战并记录未覆盖设备。

不要把一次布局树为空、旧坐标点击失败或瞬态控件淡出直接判成产品故障。先核对目标、前台 bundle、PID、截图几何、日志和测试前置条件。

## 输出与完成门槛

输出上下文与假设、状态/所有权模型、导航与适配方案、视觉与动效 Token、ArkUI 落点、验证证据和未验证项。

只有观察状态与契约一致、关键入口和失败恢复已验证、目标设备或明确替代证据已覆盖、共享路径无明显回归时才说完成。否则使用 `needs_verification` 或 `partial`。
