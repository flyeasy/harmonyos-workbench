# HarmonyOS Design

把产品任务、平台能力和真实设备证据连成一条可执行链。输出设计或代码时，始终区分：

- 长期成立的人因与状态原则；
- 随 HarmonyOS / OpenHarmony / ArkUI 版本变化的平台能力；
- 品牌、业务和项目经验形成的 House Rule。

这是独立、非官方 Skill。不要把项目建议说成华为官方规定。

## 1. 先路由任务

只选择一种主模式：

- **设计**：从需求、草图或现有产品问题建立方案与验收矩阵。
- **实现**：在用户提供的工程中修改 ArkTS / ArkUI，并完成适度验证。

遇到以下请求时不要在本 Skill 内重复展开：

- 明确要求审查、验收、评估或只报告问题：使用 `harmonyos-review`。
- 只问“这种手感叫什么、该搜什么词”：使用 `harmonyos-motion`。
- 只要求 HAP/APP 构建、设备管理、测试或发布：使用对应的 HarmonyOS 构建、设备、测试或发布 Skill。

## 2. Phase contract

1. **Input**：任务、目标窗口/输入、状态权威源和已有证据。
2. **Preflight**：确认信息架构、生命周期、设备和版本假设。
3. **Execute**：建立设计基线或完成 ArkUI 界面实现。
4. **Verify**：静态/编译后，使用 `harmonyos-targets` 固定目标并验证真实状态。
5. **Evidence**：记录状态模型、修改、截图和未验证项。
6. **Handoff**：业务实现交给 `harmonyos-develop`，体验验收交给 `harmonyos-review`。

## 3. 写最小任务契约

复用已知信息，只补会改变方案的缺口。无法确认时显式列为假设。

```yaml
主任务:
目标设备与窗口:
主要/次要输入:
目标_API_SDK:
主题_字号_语言:
当前证据:
产品状态权威源:
本轮范围:
完成信号:
验证方法:
假设:
```

不要在未确认窗口、输入和状态来源时静默套用手机触摸规则。

## 4. 先建产品真相，再画界面

在视觉和动画之前回答：

1. 哪个状态是权威事实，哪个只是本地缓存或视觉投影？
2. 状态是否混合了多个正交维度？
3. 哪个页面、组件或服务拥有这段数据和生命周期？
4. 冷启动、暖启动、返回、前后台、窗口变化和覆盖安装后会怎样？
5. 未知类型、过期响应、重复提交和失败恢复如何处理？

必要时先画状态表或转换图。不要用一个 `online/offline` 同时表达 App 链路、远端主机和会话存续；不要让“重新检查”暗示它能唤醒不可达进程。

现有工程涉及异步、跨页面、WebView、动态列表或多格式内容时，读取 [references/FIELD-PATTERNS.md](references/FIELD-PATTERNS.md)。

## 5. 建立平台与产品基线

按以下顺序决策：

1. 用户任务、信息架构与返回路径；
2. 状态权威、失败恢复与生命周期；
3. 设备、窗口、输入与内容密度；
4. 系统组件和平台默认行为；
5. 视觉 Token、字体、间距与层级；
6. 动效与手势；
7. 无障碍；
8. 性能与验证成本；
9. 品牌覆盖层。

需要细节时按任务加载：

- 原则、导航、视觉与来源措辞：[references/PRINCIPLES.md](references/PRINCIPLES.md)
- 手机/平板/折叠屏/PC、窗口和输入：[references/ADAPTATION.md](references/ADAPTATION.md)
- 动效、手势、异步状态：[references/MOTION.md](references/MOTION.md)
- ArkTS / ArkUI 能力映射：[references/ARKUI-MAPPING.md](references/ARKUI-MAPPING.md)
- 无障碍、大字体和焦点：[references/ACCESSIBILITY.md](references/ACCESSIBILITY.md)
- 官方与项目来源登记：[references/SOURCES.md](references/SOURCES.md)

只读取当前问题需要的参考文件。

## 6. 不可妥协的实现规则

### 状态真实

- 按下反馈只表示收到输入，不表示远端成功。
- 将 `acknowledged / pending / confirmed / failed` 分开。
- 旧请求不得覆盖新意图；重复提交、失败、超时、取消和乱序要有策略。
- UI 文案、成功动画和无障碍播报必须来自同一权威状态。

### 所有权清晰

- 导航状态、标签状态和页面内容分开发布。
- 页面只接收自己声明拥有或支持的数据。
- 未注册类型默认拒绝，不能默认落入文本、编辑器或通用页面。
- 监听器、定时器、轮询和手势在离开所有者生命周期时释放。
- 不在属性初始化期间调用依赖尚未创建的 `@State`、`@StorageProp` 或服务。

### 系统能力优先

- 先检查系统控件、Navigation、滚动、焦点、无障碍和默认转场。
- 自定义不得削弱按下、禁用、焦点、悬停、选中、返回或辅助工具语义。
- 不发明 ArkUI API；以目标 SDK 声明、编译和设备行为为准。

### 适配不是等比缩放

- 保持任务和信息架构，允许导航、密度、分栏和控件形态变化。
- 不只看设备名；同时看窗口、输入、交互距离和任务时长。
- 先确认窗口是否已经处理系统栏，再决定是否加 safe-area padding，避免双重避让。
- WebView、IME、工具栏和远端几何变化要分清本地覆盖与真实内容尺寸变化。

### 共享行为要真正共享

- 先盘点真实入口，不为“统一”给不支持该能力的页面硬加控件。
- 同一语义交互优先复用组件、Token 和状态契约。
- 动态列表使用稳定身份；语言、计数或状态变化必须真正触发应更新的节点。
- 弹窗关闭与列表删除避免同帧双重刷新或重入。

### 动效表达任务

- 按下即反馈，手势跟手，离手从当前速度和位置继续，并可被新输入打断。
- 临时控件或胶囊的旧计时器不得提前关闭新一轮反馈。
- `transition`、图形变换和一个 coherent `animateTo` 优先于逐帧定时器和布局属性动画。
- 动画完成不能作为业务完成时钟。

## 7. 实现流程

当用户要求修改工程时：

1. 读取项目约束、工作账本和最相关代码。
2. 复现或建立最小反例；先写预期信号。
3. 找系统性根因，避免按格式、页面或设备堆特判。
4. 设计最小兼容改动和失败关闭边界。
5. 一次完成一个连贯批次。
6. 先跑静态契约或定向测试，再编译。
7. 编译通过后安装到明确目标，验证真实状态变化。
8. 对共享服务、路由、格式或生命周期补交叉回归。
9. 做完成挑战：尝试证明本轮其实尚未完成。
10. 更新项目账本或证据记录。

详细设备循环和证据等级见 [references/DELIVERY-LOOP.md](references/DELIVERY-LOOP.md)。

默认先给计划；用户已明确要求实现并提供工程时，直接修改和验证，不再重复询问许可。没有授权时不要批量重写全部页面。

## 8. 设备验证底线

构建成功不是 UI 通过。至少检查本次相关项：

- 目标页面可进入、可返回；
- 打开/关闭、选中/未选中、按下/禁用、加载/失败；
- 快速重复、反向打断和页面重入；
- 前后台、窗口/方向变化、覆盖安装数据保留；
- 浅/深色、大字体、长文本和适用输入；
- PID、崩溃、AppFreeze、内存或长帧；
- 共享路径的交叉切换。

不要把一次 `dumpLayout` 为空、旧坐标点击失败或瞬态控件已经淡出直接判成产品故障。先核对截图、前台应用、PID、日志和测试前置条件。

## 9. 输出

### 设计模式

输出：

1. 上下文与假设；
2. 状态/所有权模型；
3. 导航与适配方案；
4. 视觉、交互和动效 Token；
5. ArkUI 落点；
6. 最小可交互原型计划；
7. 验收矩阵与未验证项。

### 实现模式

输出：

1. 已实现结果；
2. 关键设计判断；
3. 修改范围；
4. 验证证据；
5. 仍存在的风险或未覆盖设备。

不要用长篇原则复述淹没当前结果。重要结论标明 H1–H4 来源等级；推断明确写“推断”。

## 10. 完成门槛

只有同时满足以下条件才说完成：

- 观察状态与任务契约一致；
- 没有把缓存、动画或推断写成权威事实；
- 关键入口、返回、失败和恢复已验证；
- 目标设备或明确替代证据已覆盖；
- 共享路径没有明显回归；
- 未验证项和版本边界已列出。

否则使用“需要验证”或“部分完成”，不要用编译通过替代体验结论。
